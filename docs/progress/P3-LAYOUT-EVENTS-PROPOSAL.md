# Phase 3 authoritative workspace layout events proposal — 2026-10-23

## Status and scope

This is a read-only design proposal. No source, wire schema, roadmap status, or test result was changed by this review. It proposes the smallest bounded continuation of Phase 3's existing metadata watch path so clients can observe pane topology changes without polling the layout.

## Evidence and current boundary

- The current event codec is explicitly target-scoped: `Event` contains one `TargetRef`, and its bodies are `ScreenChanged`, `InputOwnerChanged`, and `ChildExited` (`src/event_protocol.rs:21-30,69-86`). The codec is metadata-only and owns no subscriptions or I/O (`src/event_protocol.rs:1-5`). A topology event can affect several targets at once, including a removed target, so representing it as an event for an arbitrary pane would give the wrong scope and lifetime.
- `EventJournal` is one generation-scoped volatile sequence, retains 64 events, and returns a bounded page after a cursor; loss before the retained boundary is an explicit `CursorExpired` (`src/event_journal.rs:13-29,74-80,106-110,145-176`). The protocol task defines 6,144 bytes of retained encoded event payload capacity and the same 64-event limit (`docs/progress/P3-NOTIFICATIONS-TASKS.md:43-61`). Current session reads first validate Read|Events capability and exact target scope, then check generation, session, and page limit (`src/server/multi_session.rs:1369-1407`).
- Reconciliation currently binds one target's screen, metadata and session journal cursor in a single owner turn (`docs/progress/P3-WATCH-INTEGRATION.md:17-22`). Its cursor identifies the server generation and session (`src/server/multi_session.rs:1341-1351`). This is valuable as a model for atomicity but is insufficient for workspace topology by itself.
- `LayoutSnapshot` is a copyable full-workspace value with a monotonically increasing revision, root dimensions, up to four spatially ordered pane geometries, and divider geometry (`src/pane_layout.rs:19-20,80-95`). The owner exposes that snapshot (`src/server/multi_session.rs:471-474`). The layout itself is volatile owner state (`src/server/multi_session.rs:132-145`).
- Layout establishment and commits happen in the multi-session owner: initial launch creates the first layout (`src/server/multi_session.rs:881-885`), split paths commit previews (`src/server/multi_session.rs:728,1040`), resize changes operate on the layout (`src/server/multi_session.rs:1093-1108`), and pane exit can collapse topology (`src/server/multi_session.rs:2619-2647`). These are the mutation boundaries at which a topology fact must be recorded after the new snapshot is authoritative.
- The current `panelink events` command already exposes the gap: it reports target metadata notifications and polls the full layout at a bounded interval for pane open/close observations (`docs/progress/P3-AGENT-CLI.md:64-68`). The watch integration explicitly lists layout changes and multiple sessions as unsupported (`docs/progress/P3-WATCH-INTEGRATION.md:93-100`).
- Retry rules say read-only snapshots may be reissued, while durable workspace mutations require the identical operation key/payload against the same generation; absolute desired-state updates require reconciliation first (`docs/SPEC.md:233-256`). Existing facts are observations and must not cause a client to replay topology mutations.

## Recommendation

Add a workspace-scoped event stream alongside the existing per-session stream. Do not widen `TargetRef`, overload `ChildExited`, or emit one fake event per pane. A layout revision is one atomic workspace fact and should have its own cursor namespace and resynchronization snapshot.

Use a fixed-capacity `WorkspaceEventJournal` owned by `MultiSessionOwner`, with a `WorkspaceCursor { generation, workspace, sequence }` (field names illustrative). For the current single-workspace prototype, the workspace ID comes from the established layout's pane targets and must be identical across all occupied entries. If that invariant cannot be validated, workspace watch/reconciliation should fail closed. The cursor still carries workspace explicitly so a future multi-workspace implementation cannot accidentally reuse one workspace's cursor for another.

The first slice should publish one event kind only: `LayoutChanged { revision }`. Each event should carry its workspace cursor and stable workspace ID, but no chosen pane target. On event receipt the consumer calls workspace reconciliation and replaces its local layout snapshot. The event is a wakeup/invalidation fact, not a patch. A later explicit design may add typed deltas if the CLI or UI demonstrates a need; the full snapshot is only four panes and is the simpler correctness boundary.

Recommended bounds: retain at most 64 workspace events in memory, expose at most 64 in one finite watch, allow no more than 8 pending workspace watches per owner, and retain the existing 1,000 ms server wait maximum, 250 ms event-batch write budget, and 2 s CLI exchange deadline. Keep workspace journal accounting separate from each session journal's 64 events / 6,144 encoded bytes. Because the proposed workspace payload is fixed and small, set and test a workspace-specific encoded-byte cap rather than treating the session cap as a shared global budget. No persistent subscription or unbounded queue is needed.

## Contract sketch

1. **Emission point and ordering.** All topology mutations run through `MultiSessionOwner`; after a mutation successfully commits `PaneLayout` and obtains its new snapshot, append exactly one `LayoutChanged(revision)` event in that same owner turn. Emit only when the committed layout revision changes. This includes initial establishment, successful split, accepted root/viewport resize that advances layout revision, and automatic collapse after a pane exit. No event is emitted for a rejected or duplicate mutation, a failed preview, or an operation that leaves the committed revision unchanged. A split's event follows the topology commit; launch still uses its existing keyed durable mutation semantics.
2. **Commit and journal error.** Layout mutation already occurred if a later journal append fails. Do not report that the layout was rolled back. Return/record an explicit notification-unavailable or unknown observation state while preserving the committed layout and live PTYs. Disable workspace notifications for that generation after cursor exhaustion or journal failure, matching the existing session-watch fail-safe (`docs/progress/P3-WATCH-INTEGRATION.md:93-97`). Snapshot/list queries remain available so clients can reconcile.
3. **Workspace reconciliation.** Add a read-authorized owner operation that, in one owner turn, copies the validated `LayoutSnapshot` (including revision) and returns the current `WorkspaceCursor`. A client starts or recovers from this snapshot/cursor pair, then watches strictly after that cursor. If no layout has been established yet, return an explicit `NoLayout` state and a valid generation/workspace-scoped zero cursor, or define an equally explicit empty-layout snapshot; this choice must be fixed before protocol coding. Do not synthesize pane targets for an empty layout.
4. **Watch and sequence.** A finite watch accepts a cursor only for the current server generation and exact workspace, rejects future sequences and invalid limits, and returns ordered consecutive records strictly after the cursor. Its terminal response carries final cursor, count, and `Changed`, `TimedOut`, or `ResyncRequired`, following existing watch semantics. If cursor history has been evicted, return `ResyncRequired` with a hint only; client must obtain a fresh workspace reconciliation before claiming current topology. Server restart changes generation and invalidates the old cursor. Sequence overflow disables workspace notifications for the generation and never wraps.
5. **Reconnect and duplicates.** Reconnection may reissue workspace reconciliation and watch as read-only observations under current state. It must never resend `split`, `close`, or other mutations based on an event, missed event, or changed generation. Durable topology mutations remain governed by `docs/SPEC.md:233-256`: same key and semantic payload only on the same generation/valid lease. Event records are not operation receipts or proof that a mutation's acknowledgment was delivered.
6. **Protocol compatibility.** Prefer new workspace request/reconciliation/watch message types or a separately versioned workspace-watch codec. Do not reinterpret the existing target-scoped request, cursor, event payload, or `TargetRef` fields. Negotiate a distinct workspace-events capability, or explicitly extend capability negotiation with mixed-version behavior before implementation. Existing clients and leases must not silently gain that capability on resume; preserve the existing rule that the Events capability is negotiated at context creation (`docs/progress/P3-WATCH-INTEGRATION.md:33-44`).
7. **Permissions.** Workspace layout is shared metadata, not a right inherited from a pane target. Require a live connection with Read plus the separately negotiated workspace-events capability. Validate workspace identity against the current owner state. Do not require a target-bound watch grant or allow a caller to learn another workspace's facts by supplying an arbitrary pane. Mutation authority remains separate; watch and reconciliation never authorize input, resize, close, or launch. Same-UID authentication remains the prototype boundary and does not isolate local agents, as the current integration notes (`docs/progress/P3-WATCH-INTEGRATION.md:93-97`).
8. **Privacy.** Emit only layout revision and bounded geometry/identity in an explicit reconciliation response. Do not include terminal bytes, command arguments, environment values, input, paste contents, provider conversation data, or secret-bearing metadata. Keep custom Debug/error output redacted consistently with session events.

## Smallest likely code touchpoints

- `src/event_protocol.rs`: keep the current 72-byte target-scoped event schema unchanged. Introduce a distinct fixed workspace-event codec (candidate `src/workspace_event_protocol.rs`) with an exact schema, one `LayoutChanged` kind, redacted Debug, strict reserved-byte validation, and golden tests.
- `src/event_journal.rs`: retain its existing per-session responsibilities. Add a distinct bounded `WorkspaceEventJournal` (same file only if the ownership stays clear; a separate `src/workspace_event_journal.rs` is easier to audit) with generation/workspace cursor, 64-event limit, checked sequence increment, expiry boundary, and bounded encoded-byte accounting.
- `src/server/multi_session.rs`: own the workspace journal alongside `layout`; add read-only `reconcile_layout` and `read_layout_events`; emit after successful committed revision changes in initial layout creation, split/resize commit, and exit collapse. Ensure event append and returned current cursor are serialized by this owner.
- `src/server.rs`, `src/server_io.rs`, `src/transport.rs`, and the relevant control/watch protocol module: add distinct message kinds, bounded finite-watch request/response handling, capability negotiation, worker validation before first byte, and the existing shared batch deadline behavior. Existing paths are target-specific (`src/server/multi_session.rs:1320-1407`); avoid routing workspace requests through `SessionHandler`.
- `src/p3_cli.rs`: change `events` topology observation to consume workspace reconciliation/watch while retaining per-target session watches for screen/owner/exit facts. On layout event, reconcile and emit one JSON topology observation. Remove the layout polling interval only after the new negotiated path works; keep a bounded fallback only if a deliberate compatibility policy requires it.
- `tests/`: codec golden/invalid cases; journal ordering, bounds, expiry, overflow; owner event counts for commit/reject/duplicate paths; atomic snapshot/cursor races; real socket finite-watch framing, capability denial, and cursor-loss reconciliation; CLI JSON and replacement-layout races.

## Acceptance scenarios for the implementation task

1. Initial single-pane layout reconciliation returns snapshot revision 1 and the exact current workspace cursor in one owner turn; subsequent watch from that cursor times out without inventing a change.
2. A successful split advances layout revision and appends one workspace event after commit. Reconciliation sees the committed two-pane snapshot and a cursor at least as new as that event.
3. A rejected split, exact duplicate split retry, stale revision, invalid resize, or no-op observation adds no extra layout event. A duplicate returns its retained operation result and does not re-execute or republish topology.
4. Confirmed pane exit followed by collapse produces one event for the new layout revision; events identify the workspace and revision, not an arbitrary surviving/removed pane.
5. A watcher racing with a topology mutation gets either an earlier snapshot/cursor followed by the event or a later snapshot/cursor after the event, never a later cursor paired with an older snapshot. Exercise deterministic owner barriers, not sleeps.
6. Retention rollover returns ordered pages while valid; a cursor older than the eviction boundary and a cursor from another generation/workspace produce explicit failure/resync behavior. Future cursors, zero/oversized limits, sequence exhaustion, malformed frames, wrong workspace, and unknown schema fail closed before response bytes are written.
7. Reconnect after lost watch response reissues only read-only reconciliation/watch. A new generation forces reconciliation. No scenario resends split/close or any other mutation from event data.
8. Workspace watch succeeds only with live Read and the negotiated workspace-events capability; target-scoped Events alone, stale lease, wrong workspace, or write-only connection is denied without exposing layout details.
9. Journal failure/cursor exhaustion after an already committed layout change preserves the new layout and child handles, reports notification unavailability/unknown observation, and leaves explicit reconciliation usable where possible.
10. The CLI produces exactly one topology JSON record per observed new layout revision, has bounded exit/deadline behavior, handles empty/no-layout state explicitly, and does not report a close/open based on a partial or stale event batch.

## Unresolved engineering choices

- Whether workspace identity is currently guaranteed by all occupied `TargetRef`s, or whether the owner needs its own stable workspace ID allocated before the first target exists. The latter is cleaner and necessary before true multiple-workspace support.
- The exact empty-layout representation before first launch and after last-pane exit. Current `layout_terminal_empty` treats an established all-exited layout as distinct from no layout (`src/server/multi_session.rs:451-474`); preserve that distinction.
- Whether resize that changes only root dimensions should notify layout watchers, and whether focus/zoom/selection are part of this topology event stream. Recommended now: notify for any committed `LayoutSnapshot.revision` change; do not add focus/zoom until their ownership and revision contracts are settled.
- Exact wire schema/version and capability bit allocation, including behavior for existing saved client contexts and older servers. This requires protocol version compatibility review before coding.
- Whether workspace event sequence is per workspace or one generation-wide stream tagged by workspace. Recommended for multiple workspaces: per-workspace cursor, with generation and workspace in the cursor; current prototype can still host one such stream.
- Whether event append can be made infallible after layout commit by preflighting the next sequence and reserving journal capacity. Strong recommendation: preflight checked sequence/capacity before commit so a topology mutation does not commonly commit without its event; retain the explicit failure policy for catastrophic/internal inconsistency.
- Whether the CLI should fully remove polling once capability negotiation exists or keep an explicit bounded legacy fallback. Do not make polling a hidden correctness dependency.
