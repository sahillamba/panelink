## Approved prototype limits

Keep existing per-operation65536bytes, per-lease1024operations and TTL1800s. Add public constants MAX_LEASES_PER_GENERATION=4096 (including permanent expired lease records), MAX_ACTIVE_LEASES=64, MAX_RETAINED_OPERATIONS=4096 (across all leases, includes retained expired pending/completed metadata), MAX_RETAINED_PAYLOAD_BYTES=8*1024*1024. These are source/accounting ceilings, not measured RSS or final user product limits. No configurable limits in this slice. Exhaustion fails closed; never evict a live admission or forget a lease ID to make room. A finite ever-opened lease bound intentionally exhausts the generation eventually; no automatic server restart/rollover is implemented or implied.

Preserve existing public APIs/semantics while adding:

- LedgerUsage, Copy/Debug/Eq/PartialEq, with public documented usize fields lease_records, active_leases, retained_operations, retained_payload_bytes. Ledger::usage(&self)->LedgerUsage returns stored-record counts, no clock and no secrets. Active means not yet marked expired by explicit maintenance; callers must run maintenance to reclaim due records.
- ProtocolError variants LeaseCapacityExceeded (ever-opened), ActiveLeaseCapacityExceeded, GlobalOperationCapacityExceeded, PayloadCapacityExceeded and LeaseIdExhausted, all redacted fixed labels. Keep old per-lease CapacityExceeded.
- Ledger::issue_lease(&mut self,now_secs:u64)->Result<u64,ProtocolError>. Start at1; allocate strictly above all successfully opened IDs, including those opened using legacy open_lease. Checked addition, never wrap/reuse. Failed opens/issue do not consume IDs/capacity or alter time/sequence watermarks. open_lease remains compatibility foundation API; future server must expose only issue_lease. Generation is still caller-supplied; no durable generation allocator or authentication claim.
- Ledger::expire_leases(&mut self,now_secs:u64)->usize returns count newly marked expired. Explicit maintenance scans at most4096lease records and4096operation records. For leases with now>=expiry or already marked expired: irreversibly mark expired, decrement active count once, release ALL payload allocations (replace Vec with empty Vec, not only clear), delete terminal operation metadata and decrement operation count accordingly. Keep pending operation identities/state with empty payload, preserving completion after expiry. Never admit/status/renew/receipt/open an expired lease again even with earlier timestamps after this marking. Expiry is maintenance, not cancellation. Accepted pending entries remain under global operation cap. Completion after expiry may retain its fixed metadata until next expire_leases call; then terminal metadata retires. Maintenance of already-expired leases must also reclaim newly completed records. Permanent lease ID plus highest/retired sequence metadata prevents redispatch. No zeroization guarantee for freed allocator memory.

Document expiry retirement: complete remains idempotent for an outcome while its fixed record is retained. Once explicit expiry maintenance removes a terminal record, complete for that sequence returns ResultExpired, matching the existing retired-result boundary; do not return UnknownOperation for known retired IDs. Public status always LeaseExpired for expired leases. Maintenance may advance an expiry retirement watermark to highest_sequence, but complete must look up retained pending records before that watermark so they can complete. Alternatively preserve original retirement watermark and track expiry retirement via expired flag/highest_sequence. Whichever is used, skipped unknown old sequences must not become dispatchable. Expired-result retention isn't a persistent journal or observable status history.

Existing mutating APIs need not run maintenance automatically: capacity failures and invalid requests must leave stored ledger counters/IDs/watermarks unchanged. Expired timestamps reject requests as before but do not silently reclaim unrelated records; expiry reclamation is the explicit method above. Caller must supply monotonic time and schedule maintenance in future server. complete has no timestamp and cannot infer a newly due lease before maintenance. These limitations must be explicit in docs.

Admission must validate generation/lease/sequence/expiry/payload, compare a known duplicate BEFORE global capacity checks, and reject conflicts even under full capacity. Only a NEW key charges operation/payload counts and reserves before Execute. No counters/watermark changed on cap rejection. Empty payload still charges an operation slot. Checked arithmetic for byte counts; global cap checks before copying payload. Receipt prechecks all pending and highest conditions, then removes terminal records and subtracts exact byte/count charges; no underflow or double release for repeated receipts. Keep pending work across expiry and never cancel/replay it. Custom Debug contains only numeric metadata, never payload. Retained payload bytes describe logical owned bytes with bounded containers/metadata, not allocator/RSS measurement.
