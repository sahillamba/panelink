# Phase 3 live pane metadata proposal

Status: bounded design discovery, 2026-10-23. This is an engineering proposal, not an accepted product decision or implementation evidence. No source, dependency, or protocol changes were made for this note.

## Current boundary

`TerminalSession` owns `std::process::Child` and its PTY in `src/terminal/mod.rs`; `spawn` receives a `ResolvedLaunch`, calls `Command::new(launch.executable_path)`, and sets `current_dir(launch.working_directory)`. The resolved values are absolute/canonical launch-time paths (`src/launch.rs`, `ResolvedLaunch`). The child handle is currently private; there is no public read of its PID or a live process metadata query. The CLI's pane JSON explicitly emits `cwd:null` and `command:null` in `src/agent_cli.rs::push_pane_json`, and `docs/progress/P3-AGENT-CLI.md` records these nulls as a current query limitation. Pane status is assembled through `PaneReply` in `src/multi_runtime.rs`, with server-side metadata/layout synchronization in `src/server/multi_session.rs`.

These sources answer different questions:

* The prepared launch record answers what Panelink resolved and requested at spawn. It remains useful as provenance/fallback information, but it becomes stale after `cd`, `chdir`, or `exec`.
* The direct managed child PID answers the current directory and executable image of that child when sampled. It does not answer which descendant is currently foreground in the PTY. Shell jobs and commands normally have different PIDs; a shell can itself `exec` a new image.
* The foreground process group is a separate, potentially changing process set. Supporting it needs a separate contract, and must not be implied by fields named `cwd` or `command`.

Do not silently fill current fields with launch values. Preserve the distinction in the query contract.

## Proposed smallest useful contract

Add a read-only, per-pane `process` observation containing `cwd` and `executable` independently. Each value is either `{ "value": <safe string>, "source": "managed_child", "sampled_at_mono_ms": N }` or `null`; add a bounded shared status such as `process_observation: "available" | "partial" | "unavailable"` and a fixed reason enum for unavailable data (`exited`, `permission_denied`, `process_gone`, `unsupported`, `invalid_path`, `query_failed`). Include a process-instance discriminator internally (server generation + managed-session ID + captured PID + OS start time where available) so a PID reused during a query cannot be attached to another child. Do not return PID to the ordinary pane JSON unless a separate product need is accepted.

On platforms where query support is implemented, sample the *owned direct child's* current process image and cwd. On non-macOS/unsupported platforms return explicit unavailable, not launch-time substitutes. If retaining launch information is useful, expose it under clearly named `launch.cwd` and `launch.executable` fields with source `resolved_launch`; do not conflate these with current values. A simpler first slice may omit launch fields entirely and retain them internally.

Freshness is observation-time, not a promise that the process still has that cwd when the client renders it. Return a monotonic sample timestamp and document it as a point-in-time, best-effort observation. The owner loop must not synchronously block on process queries: use a bounded query worker or cached latest observation, with a short fixed deadline and a finite response size. Query failure or timeout leaves the current sample unavailable/stale and never blocks PTY pumping, shutdown, input, or event delivery. No event is required for every `chdir`; clients can refresh with a read query. Any future metadata event must carry sample time/revision and cannot claim atomicity with layout or screen state.

## macOS source feasibility and binding boundary

The local macOS SDK `libproc.h` declares `proc_pidinfo` and `proc_pidpath`. The current pinned `libc = 0.2.191` is present in `Cargo.toml` and lockfile but its Apple module has no declarations for these `libproc` calls. The SDK exposes `PROC_PIDVNODEPATHINFO` data (`proc_vnodepathinfo.pvi_cdir.vip_path`) for cwd and `proc_pidpath` for the current executable image. These APIs query the specified PID; they do not identify the PTY's foreground command. `proc_pidinfo`'s byte-count result must match the expected structure size; a short/zero result is unavailable, not a partially trusted path. `proc_pidpath` has a caller-supplied output buffer and may return failure or truncation; use a fixed `PATH_MAX`-bounded buffer and reject nonpositive, over-capacity, unterminated, or invalid data. The kernel-returned vnode path is a fixed-size byte array and must likewise be bounded and terminated.

Current sources show direct-child ownership and an existing PID wrapper (`Pid::from_child`), but no current metadata accessors. The launch inputs are already validated as absolute paths without NUL; actual process results need their own validation. The narrow OS-query seam would likely be a new `src/process_metadata.rs` plus a crate-private `TerminalSession` snapshot method and `multi_runtime` reply plumbing. The process identity should be captured alongside child ownership at spawn, and revalidated around the query using PID plus OS process start time (`PROC_PIDTBSDINFO` start-time fields), because a child may exit and its numeric PID may be reused. If exit is observed before/after the sample, report unavailable. A mismatch, racing exit, or inconsistent result also reports unavailable. No signal or other side effect is performed.

Important implementation constraint: calling the SDK functions from Rust requires declarations and the C layouts/constants. This is not currently supplied by the pinned Rust `libc` crate. Before implementation, determine whether an approved existing crate/toolchain binding already exposes the APIs; otherwise a minimal audited `extern "C"` boundary and SDK-derived layout/constants is necessary, which is effectively a small handwritten OS binding and must be reviewed explicitly against the project policy. Do not assume that the mere presence of `libc` means these symbols/types are available. No dependency should be added just to make this proposal work without full dependency review.

## Safe encoding and privacy

Process paths are local metadata, but can expose usernames, private directory names, mounted volumes, and project names. They should be available only to the existing local read authority, omitted from diagnostics/journals/history, and never copied into saved layout/recovery metadata unless separately reviewed. Do not read process arguments, environment variables, credentials, or shell state. Do not parse `ps`, shell output, or terminal escape/OSC hints.

Encode paths as bounded JSON strings using the existing JSON string escaping helper. Require an absolute path, cap each encoded field (suggested initial cap: 4 KiB UTF-8 bytes), escape control characters through JSON escaping, reject embedded NUL, and never lossy-decode silently. macOS filesystem paths are arbitrary bytes: if bytes are not valid UTF-8, return an explicit `invalid_path`/unrepresentable status (or a future separately reviewed byte encoding), not replacement characters. Truncate only at a valid Unicode boundary if a documented truncation marker/status is added; preferably reject oversize values as unavailable to avoid presenting a misleading path. Ensure `Debug` and error output contain only fixed reasons, never returned paths or raw OS error strings.

## Touchpoints and scoped acceptance

Likely touchpoints, subject to source review at implementation time: `src/terminal/mod.rs` (`TerminalSession` child ownership and spawn-time identity), new `src/process_metadata.rs` (macOS bounded query and cross-platform unavailable result), `src/multi_runtime.rs` (`PaneReply`), `src/server/multi_session.rs` (single metadata/reply composition), control/UI protocol types and codec where pane metadata crosses the socket, `src/agent_cli.rs` (replace nulls and preserve JSON escaping), and `docs/progress/P3-AGENT-CLI.md`/`docs/SPEC.md` (only after contract acceptance). The `src/launch.rs` resolved launch values may populate explicitly named launch provenance fields but must not be treated as live values.

Minimum implementation evidence should cover: initial cwd/executable; child `chdir` reflected after refresh; direct child `exec` reflected after refresh; a spawned foreground descendant does not replace the direct-child identity; exit/PID-reuse race fails closed; unsupported/permission/error/short-read results; invalid UTF-8, control bytes, NUL, and over-capacity paths; bounded deadline while the child is busy; and proof that argv/env are never queried. These are proposed checks, not completed tests. Foreground-job metadata remains an engineering option for a later, separately named contract.

## Evidence limits and open choices

The investigation used the current worktree's indexed graph (project `Users-sahillamba-.codex-worktrees-6730-panelink`, status ready), direct source and local SDK header inspection. The graph is discovery assistance; checked-in source is authoritative. This pass did not compile a macOS API probe or verify a Rust binding, so binding availability and exact OS struct ABI still require an implementation-time primary-source check. Product decisions still open: whether to expose launch provenance alongside current observations, whether to add foreground-process-group metadata, the exact freshness/deadline/size limits, and whether non-UTF-8 paths should remain unavailable or receive a reviewed byte-safe representation.
