## Engine corrections, bounds and maintenance cost

Upstream archive: vt100 0.16.2, SHA-256 `054ff75fb8fa83e609e685106df4faeffdf3a735d3c74ebce97ec557d5d36fd9`, upstream VCS metadata `eb66ffaf7d771c13303ef73b29f6f2a56fdacecf`. Local package version is distinct. The parent inspected each source diff and independently reran the final nine engine-probe tests and capacity example after a Luna xhigh feasibility review.

The corrections disable VTE defaults (fixed 1,024-byte OSC array), cap extra combining scalars at eight, clamp cell insertion before allocation, clamp repeated line-insert/scroll-down work, and drop VTE-ignored CSI before dispatch. These changes remain within the selected library; Panelink does not add a second parser. The MIT author notice and upstream README/changelog/original manifest are retained. No generator or upstream installer ran. See the preserved [engine source/probe report](p2-core-review/ENGINE-PROBE.md) for exact evidence and actual outputs.

Use 1,024 normal history rows and zero alternate history, within the proposed 2,000-row ceiling. Smaller history is a prototype budget, not a product retention decision. Dimensions remain 5–80 rows and 20–240 columns. The adversarial width-239 → 240 → 240 inserted cells path retained capacity 956 for 240 visible cells on Rust 1.99.1; the model reserves 1,024 cell slots per row. The parent reproduced that result. A 32-byte cell, row/container capacities, fixed parser, input/events and two generously budgeted visible snapshots yield 63,088,640 bytes (60.17 MiB) under the report's assumptions. The actual core must enforce every dimension/history/queue/snapshot limit and avoid cloning history. This is a source/container model conditional on the tested toolchain, not an RSS measurement or a portable theorem about excess Vec capacity. Repeat the capacity/feature review on toolchain or dependency changes; the installed `stable` selector is not an exact reproducibility pin.

Parent additionally inspected the installed toolchain's generated `alloc/raw_vec/mod.rs` source, lines 519–532: amortized capacity is the maximum of twice the old capacity, the required capacity, and a small type-dependent minimum. `VecDeque::reserve` uses that RawVec path (`collections/vec_deque/mod.rs:1114`). [Installed-source fingerprints](p2-core-review/container-source.json) record this evidence. With bounded row length at most 480 during insertion and initial/resize width at most 240, retained cell capacity stays below the rounded 1,024-slot budget on this implementation. A 2,048-slot `VecDeque<Row>` reserves **row metadata only** (65,536 bytes), not cell backing for 2,048 live rows: at most 1,024 history rows plus one transient row own cell allocations. Do not double-count every spare deque slot as a constructed inner cell vector. The source-derived model and the capacity example agree; allocator/system RSS is a separate measurement.

VTE truncates oversized OSC and can dispatch a prefix at termination. This establishes a preallocation storage bound, not complete validation/rejection of the original string. All title/link/clipboard-write callbacks must drop content synchronously without retaining/copying it; only the four strict supported CSI query replies are allowed; clipboard reads receive no reply (corrected2026-10-18 after empty replies reached shell input). The byte limit can truncate combining text before eight extra scalars; no universal grapheme/Unicode-rendering promise.

[VT100 upstream](https://github.com/doy/vt100-rust) was not archived in the read-only repository check; last push reported 2025-07-12. The inspected [Rustix](https://github.com/bytecodealliance/rustix) and [openpty](https://github.com/sunfishcode/rustix-openpty) repositories were not archived and reported pushes 2026-10-15 and 2025-03-06 respectively. These are dated maintenance observations, not future-support promises. The local correction increases Panelink's review/maintenance responsibility; accept that burden only for this bounded prototype and reconsider upstreaming or replacement before release. No upstream submission/message was made.

## PTY source/API review and actual probe

`rustix-openpty` 0.2.0's macOS `openpty` path calls the platform function, wraps both fds in OwnedFd, then sets CLOEXEC. Failure paths close owned descriptors. `Pty` has no custom Drop that sends input or waits. CLOEXEC is not atomic on macOS: serialize all Panelink PTY creation/child spawns. This does not protect against unrelated external threads/libraries spawning independently.

Rustix's `setsid`, controlling-terminal ioctl, terminal-size ioctl, flag and group-signal wrappers propagate OS failures. The proposed application has one documented unsafe `Command::pre_exec` registration; its child hook must call only the reviewed async-signal-safe session/controlling-terminal wrappers, with no allocation/locking/logging/environment reads. Follow [Rust's pre_exec safety contract](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html#tymethod.pre_exec). Use `Command::env_clear` plus only the supplied map and `current_dir`; promptly drop the Command and all parent slave references after spawn. Never use a helper that masks a failed setsid/cwd.

A separate Luna xhigh disposable Rustix probe passed four tests on aarch64-apple-darwin. The parent independently reran them: exit 0, four passed, zero doctests. Actual evidence: all three child stdio fds are TTYs, `/usr/bin/env` receives exactly the synthetic marker and TERM (no parent PATH or injected SHELL), cwd is exact, nonexistent cwd fails without running the marker child, initial size is 24×80, resize is 37×111, and a HUP-ignoring child is KILLed/reaped within the one-second HUP plus one-second KILL windows. Probe path: `/private/tmp/panelink-rustix-pty-probe`; sources there are disposable. This proves API viability, not the yet-to-be-built application adapter. Group cleanup does not control descendants that leave the group/session. Timeout and Drop repeat-attempt behavior must be addressed in the application, beyond the successful probe path.
